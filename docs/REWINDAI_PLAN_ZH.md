# VideoRAG 学习工作台：产品与研发计划

> 项目阶段：规划草案｜目标用户：需要复习课程录像的大学生｜项目定位：可验证的多模态视频学习工具

## 1. 项目概述

本项目计划基于 [VideoRAG](https://github.com/zhuzhenxiang93-create/VideoRAG) 构建一个课程视频学习工作台。学生可以添加课程录像、针对视频内容提问，查看带时间戳的证据，并保存需要复习的片段。

**一句话价值：让学生更快地找到课程录像中的相关内容，并能回到原视频验证 AI 回答。**

例如，学生想复习“Transformer 中 attention 的作用”，却不记得是哪一分钟。系统根据课程内容返回简短回答、相关视频片段和时间范围；学生点击证据跳转到播放器，再将有用的片段保存到复习清单。

本项目是学习与作品集规划，不预设自己发现了独一无二的需求，也不预设系统已经达到生产可用水平。最终方向应根据用户访谈和试用结果调整。

## 2. 项目目标与适合展示的能力

### 产品目标

- 帮助学生定位长视频中的知识点，减少反复拖动进度条的时间。
- 让学生知道回答依据来自哪里，并能查看原始片段。
- 帮助学生整理需要再次观看的内容。
- 在证据不足或模型不确定时，明确告知用户。

### 作品集目标

项目可以展示以下能力：

1. **用户与产品思考**：理解学生的复习流程，决定功能优先级。
2. **多模态 AI 应用**：结合语音、文本与视频画面进行检索。
3. **可靠性设计**：展示来源、处理无答案问题、允许用户反馈。
4. **实验与评估**：对比不同检索方案，分析错误和性能代价。
5. **产品交付与沟通**：通过演示、文档、用户测试和结果说明项目价值。

目标岗位包括 AI Product Intern、Applied AI Intern、AI Solutions Intern、AI Business Analyst Intern 等；具体岗位职责需以招聘说明为准。

## 3. 用户与需求

### 核心用户

**需要使用课程录像复习知识点的大学生。** 首个版本优先服务单个学生，使用少量已获授权的课程视频；不先建设校园级系统。原仓库主要面向中文视频，英文课程视频的转录、检索和回答效果需要单独验证。

### 典型场景

- **课后复习**：找到老师解释某个概念的位置。
- **准备考试**：收藏不理解的片段，并记录复习笔记。
- **补看遗漏内容**：从录像中定位某张幻灯片或某个例子。

### 待验证的假设

以下是项目假设，不是已经验证的事实：

- 学生在长视频中查找知识点时会花费较多时间。
- 相比只有文字回答，带准确时间戳的回答更便于检查和继续学习。
- 某些问题需要视频画面才能回答，仅靠语音转录不够。

通过访谈和任务测试检验这些假设。如果实际用户更需要课堂笔记或跨课程搜索，可以相应调整优先级。

## 4. 第一版范围（MVP）

围绕一条核心流程：**添加视频 → 提问 → 查看证据 → 跳转 → 收藏**。

| 功能 | 第一版内容 | 完成标准 |
| --- | --- | --- |
| 课程与视频 | 创建课程、添加少量视频、显示处理进度和失败原因 | 用户能够找到已处理的视频，并了解是否可提问 |
| 视频问答 | 对指定视频或课程提问，返回基于已有内容的回答 | 正常问题有回答；证据不足时明确提示 |
| 证据与跳转 | 展示视频名称、时间范围和相关文本或画面线索 | 点击时间戳可跳到对应视频位置 |
| 复习清单 | 收藏片段并添加、编辑或删除个人备注 | 用户重新打开后仍能找到收藏 |
| 反馈 | 对回答和证据分别标记有用或无用，可填写原因 | 反馈可追溯到问题与对应结果 |

**先不实现**账号体系、班级协作、复杂权限、自动考试评分、移动端 App 和大规模部署。这些可以在基础体验得到验证后再评估。

## 6. 使用流程与界面草图

### 学生使用流程

1. 新建课程，例如“人工智能基础”。
2. 添加有权使用的课程视频，查看处理状态。
3. 选择视频，输入问题：“这段课是怎样解释 attention 的？”
4. 阅读回答，查看证据的文字、画面线索和时间范围。
5. 点击时间戳跳转到视频，确认回答是否准确。
6. 收藏关键片段并添加备注；如结果不准确，提交反馈。

### 首版界面

```text
┌─────────────────────────────────────────────────────────┐
│ 课程列表       │ 课程视频                  │ 复习清单    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  视频播放器                         问答区域              │
│  [播放 / 暂停 / 时间轴]              输入问题             │
│                                    AI 回答               │
│                                    证据：12:30–13:10     │
│                                    [跳转] [收藏]         │
│                                    [有用] [无用]         │
└─────────────────────────────────────────────────────────┘
```

界面草图仅表示产品结构，不代表原仓库已经实现相同布局。

## 7. 技术方案

### 7.1 处理流程

```text
课程视频
  ├─ 语音识别 → 带时间戳的转录文本 ─┐
  └─ 关键帧提取 → 画面相关信息 ──────┤
                                    ↓
                           视频切片与索引
                                    ↓
用户问题 → 检索候选片段 → 排序 → 基于证据生成回答
                                    ↓
                     回答 + 来源 + 时间戳 + 反馈入口
```

具体的模型、检索和部署方式以验证后的代码为准，不假设所有模型都在第一版中同时运行。

### 7.2 系统模块

| 模块 | 职责 | 实施原则 |
| --- | --- | --- |
| 视频处理 | 导入视频、提取语音与关键帧、记录进度 | 复用已有流水线，失败时给出原因 |
| 检索与生成 | 根据问题返回候选片段和回答 | 明确区分检索证据和生成内容 |
| 学习界面 | 播放、提问、跳转、收藏、反馈 | 优先完成一条可演示流程 |
| 数据存储 | 保存课程、视频、片段、收藏和反馈 | 原型可使用轻量数据库，后续按需要调整 |
| 评估 | 测试检索、答案、时间戳和无答案处理 | 使用独立人工核验的数据，记录评估方法 |

### 7.3 关键技术问题

- **时间戳对齐**：语音片段和关键帧要对应正确的视频时间范围。
- **证据质量**：找到相关片段不代表该片段足以支持回答，需要分别核验。
- **画面信息**：关键帧可能漏掉图表或文字；是否需要 OCR 应在测试后决定。
- **无答案处理**：无法找到足够证据时，提示用户，而不是编造内容。
- **性能与成本**：记录视频处理时间、问答等待时间和模型资源占用。

### 7.4 运行资源与替代路径

原仓库 README 对完整流程建议使用 Ubuntu、至少 24 GB 显存、64 GB 内存和至少 100 GB 磁盘。这是作者建议的复现环境，不代表其他配置一定无法运行；应先用实际设备验证。

仓库有 CPU 演示模式，但其脚本使用预设片段和简化组件，不能以此证明完整多模态模型的效果。可考虑：

1. 用 CPU 演示检查界面和基础流程。
2. 用小型授权视频测试各处理阶段，记录实际资源消耗。
3. 如果本机资源不足，评估按量计费的云 GPU 或可用的远程模型服务，并先估算费用和数据处理条件。
4. 先完成文本检索对照组，再根据可用资源接入视觉流程。

### 7.5 素材与数据处理

优先使用自制或明确授权的演示视频。避免上传含学生姓名、声音或其他个人信息的录像，除非已获得相应许可。使用云模型前，先确认视频、音频、转录或截图是否会发送给服务商及其处理条款；个人测试数据、索引和反馈应支持清理，不将原始课程素材或密钥提交到公开仓库。

## 8. 评估计划

### 8.1 构建人工核验问题集

选取少量有权使用、内容不同的课程视频，由人工观看并编写问题、参考答案和支持答案的时间范围。可先从 **30–50 个问题**做试点，再按实际情况扩展；这是项目建议，不代表现有数据规模。

问题至少覆盖：

- **语音类**：主要依据讲师所说内容。
- **画面类**：需要查看幻灯片、图表或屏幕内容。
- **综合类**：需要结合语音和画面。
- **无答案类**：视频里没有足够信息。

避免把同一视频的相邻片段同时放入用于调参和最终测试的数据中。优先按视频划分开发集与测试集；最终测试集保持不参与调参。数据少时明确报告局限，不把试点结果当成全面结论。

### 8.2 对照实验

| 实验 | 输入和方法 | 要回答的问题 |
| --- | --- | --- |
| A：文字基线 | 语音转录文本检索 | 只看讲师说的话能做到什么程度？ |
| B：多模态方案 | 转录文本加关键帧相关信息 | 画面信息是否改善了画面类和综合类问题？ |

尽可能使用同一批问题、相同的视频划分和相同评估标准。记录模型配置与运行条件，不要只比较两个最好的案例。

### 8.3 指标和记录

| 维度 | 如何检查 |
| --- | --- |
| 检索质量 | 相关证据是否出现在前 K 个结果中，可报告 Recall@K |
| 时间戳质量 | 人工检查跳转片段是否覆盖支持答案的位置 |
| 回答质量 | 人工判断回答是否正确、是否得到引用证据支持 |
| 无答案处理 | 单独统计应拒答的问题中，系统是否明确表示证据不足 |
| 用户体验 | 记录任务完成情况、查找时间和用户反馈 |
| 运行成本 | 报告处理时间、问答延迟；可获得时记录模型与计算费用 |

按问题类型分别报告结果，并记录错误示例。评估初期人数和样本较少时，应写明结果只反映试点。

### 8.4 用户试用

邀请 3–5 名愿意参与的同学进行探索性测试：每人完成若干具体任务，记录是否找到正确片段、耗时、遇到的困难与反馈。受试者人数少，结论用于发现问题，不用于推断整体市场需求。使用课程录像前先获得必要授权。

## 9. 研发阶段与交付物

时间以个人实际投入和硬件资源为准；以下为建议顺序，不是固定工期。

如果每周能稳定投入，可以先按 **4–6 周**安排：第 1 周完成可行性验证，第 2–3 周完成核心流程，第 4–5 周进行评估和试用，最后整理作品集。实际时间会受硬件、视频处理时间、授权和开发经验影响。

### 阶段 0：确认基础与可行性

- 确认仓库使用授权、素材许可和目标设备配置。
- 阅读原仓库代码及文档，记录已有与尚未验证的功能。
- 运行 CPU 演示；尝试在预算内验证一小段视频的真实处理流程。
- 确定用户、场景和第一版范围。

**交付物**：运行记录、资源与费用估算、项目范围说明。

### 阶段 1：完成核心流程

- 完成视频列表或课程组织。
- 接通问答、证据展示和时间戳跳转。
- 增加处理状态、失败提示和证据不足提示。
- 用少量授权素材完成端到端演示。

**交付物**：可演示的原型与基础使用说明。

### 阶段 2：增加学习流程

- 增加片段收藏、备注和持久保存。
- 增加答案与证据反馈入口。
- 梳理 3–5 个用户任务，检查主要交互是否清晰。

**交付物**：可完成“提问—验证—收藏”的版本。

### 阶段 3：实验与用户反馈

- 建立人工核验问题集和按视频划分的测试集。
- 比较文字基线和多模态方案。
- 进行小规模用户试用，整理失误和改进建议。
- 优先解决一个对用户影响最大的实际问题。

**交付物**：实验记录、局限说明和用户反馈总结。

### 阶段 4：作品集展示

- 录制 2–3 分钟演示，展示一次真实的端到端任务。
- 撰写产品案例：问题、用户、方案、取舍、结果和下一步。
- 完善 GitHub README 和运行说明，清楚标记原仓库与个人贡献。
- 在简历中使用真实验证过的结果，不编造用户数或提升百分比。

**交付物**：项目仓库、演示视频和产品案例说明。

## 10. 用户故事与验收清单

### 用户故事

- 作为学生，我想提问并看到相关视频片段，以便快速复习。
- 作为学生，我想查看回答依据，以便判断回答是否可靠。
- 作为学生，我想保存片段并写笔记，以便考试前再次查看。
- 作为学生，我希望系统在没有找到答案时告诉我，而不是给出没有依据的结论。

### 第一版验收

- [ ] 已确认代码、模型与素材的使用授权。
- [ ] 用户能添加或选择视频，并看到处理状态。
- [ ] 处理完成的视频可以被提问。
- [ ] 至少一个相关证据可点击跳转到对应视频时间。
- [ ] 证据不足时，界面显示明确提示。
- [ ] 用户可以收藏片段、查看收藏并添加备注。
- [ ] 用户能反馈答案或证据的问题。
- [ ] 至少完成一组人工核对的问题测试并记录失败案例。
- [ ] README 清楚说明环境、运行方式、限制和个人贡献。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 完整模型资源需求高 | 本机无法完成全部推理 | 先验证简化流程，再评估云 GPU、远程服务和预算 |
| 课程视频授权不明确 | 无法公开演示或分享素材 | 优先使用自制或明确授权的视频，保留来源 |
| 自动生成问题集不可靠 | 评估结果可能失真 | 人工观看视频并核验测试题与证据 |
| 相关片段不支持回答 | 用户被错误信息误导 | 提供跳转核验、证据反馈和无答案提示 |
| 需求范围过大 | 长时间无法交付 | 先完成单用户、少量视频的核心流程 |
| 产品与现有工具相似 | 难以讲清价值 | 聚焦课程复习流程，以用户测试验证取舍 |

## 12. 后续可选方向

第一版完成、且用户反馈支持后，再考虑：跨视频检索、课程总结、自动复习题、教师资料管理、团队共享或企业培训场景。每个功能都应有明确用户需求和可验证的验收方式。

如果希望加入 Agent，可以先让它完成范围清晰的流程，例如整理用户已收藏的片段并生成复习提纲；要求保留来源并允许用户修改。是否加入 Agent 应取决于用户价值，不以 Agent 数量作为目标。
